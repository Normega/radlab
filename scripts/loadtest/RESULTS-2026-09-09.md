# Ramp test — 2026-09-09, the night after PSY240 L1

Run to answer one question: **how many concurrent students does the current
compute size actually hold?** It answered that, found two product bugs on the
way, and was stopped early for reasons worth recording.

Harness: `scripts/loadtest/` (README there for the design). Target: the
**production** main Supabase project, against a scratch `loadtest` class.

---

## The short answer

**`small` is not remotely stressed by a class this size.** At 113 concurrent
students the database peaked at **2.4% CPU**. Write latency was *flat* —
151 ms at 25 students, 160 ms at 113. Nothing bent.

For contrast, the instance that died during L1 (`nano`, 0.5 GB, shared
burstable CPU) pinned at 100% and stayed there. The upgrade was the fix, and
it has roughly two orders of magnitude of headroom at the tested range.

## Numbers

| Level | Actually connected | sign-in p95 | fan-out p50 / p95 | write p50 / p95 | poll p95 | errors | client lag |
|------:|------:|------:|------:|------:|------:|------:|------:|
| 25 | 25 | 374 ms | 136 / 136 ms | 151 / 158 ms | 159 ms | 0 | 16 ms |
| 50 | 50 | 350 ms | 607 / 609 ms | 151 / 158 ms | 155 ms | 0 | 16 ms |
| 100 | **81** | 462 ms | 348 / 351 ms | 133 / 157 ms | 157 ms | 6 | 17 ms |
| 150 | **113** | 503 ms | 167 / 168 ms | 160 / 160 ms | 162 ms | 0 | 17 ms |

Server-side, sampled every 20 s from the privileged metrics endpoint
(`metrics.mjs`):

| | idle | at 150 |
|---|---|---|
| CPU | 0% | **0–2.4%**, peak 9.5% during a 50-user burst |
| Memory | 0.68 GB (38%) | 0.70–0.89 GB, oscillating with GC — **no upward trend** |
| Disk busy | 0% | ~1% |

Instance: 2 vCPU, 1.79 GB. Database is **57 MB** with a 94% cache hit rate —
the whole thing fits in `shared_buffers` several times over, which is why
memory was never going to be the constraint. `max_connections` is 90, of which
~21 are held at idle by Supabase's own services.

**No knee was found.** p95 write never rose above 2× its floor.

## What the test could not reach, and why

The levels above 50 **did not reach their target**: 81 of 100, 113 of 150. The
edge logs show steady **429s** — Supabase Auth refusing sign-ins.

This is a **harness artifact, not a student risk**, established afterwards:
the harness signs in with `signInWithPassword`, a path students never touch.
Real students go `/api/roster-join` → `admin.generateLink` → Resend → click →
`verifyOtp`. All 300 clients also came from one residential IP, and these
limits are typically per-IP.

So the concurrency figures above are *lower bounds on what was offered* and
accurate for what actually connected.

## Two product findings

**1. Closing a check-in destroys answers in progress.** Simulated students wait
3–28 s before answering, as real ones do. When the script closed a check-in,
anyone still composing got `new row violates row-level security policy` and
lost their text. Six hit it here; **four real students hit it during L1**. The
RLS gate is `status = 'open'`, and closing is instant.
*Still open.* A grace period, or a gentler client-side message, would fix it.

**2. The console swallowed refused actions.** Pressing Play on a second
check-in was rejected by `enforce_single_live_checkin`, and the error rendered
in a banner *above the whole check-in list* — off-screen on a page with six
check-ins. It looked like a dead site. Plausibly part of what L1 felt like.
*Fixed* 2026-09-10: errors are now scoped to the card that produced them and
translated into instructions.

## Harness bugs found by running it

Recorded because they cost the run, and because the first one would have
silently corrupted the results rather than failing loudly.

- **`reset_checkin()` was failing silently between levels.** It gates on the
  caller being a class admin, and a service key has no `auth.uid()`. Every
  level would have opened a check-in still holding the previous level's
  responses. Now deletes directly with the service role.
- **Response dedupe keyed on check-in id.** The ramp rotates through three
  positions, so a check-in used at level 2 reopens at level 5 — and every
  worker had already "responded" to it. **Levels 200/250/300 would have
  produced zero writes**: exactly the levels the test exists to measure. Now
  keyed on `id:opened_at`.
- `rpc()` returns a thenable builder, not a Promise — `.catch()` on it threw.
- Sign-in samples were collected and then discarded by the drain, so that
  column could only ever print `—`.

## Mistakes made against production

Recorded in full, because the containment design was meant to prevent exactly
this and did not.

**A PATCH without a class filter reset four real check-ins.** Cleaning up
between levels, `UPDATE checkins ... WHERE position IN (1,20,40,70,71) AND
status <> 'planned'` was run with no class predicate. It set PSY240 L1's
arrival check-in (**53 student responses**) and PSY309 L1's position 40 (12
responses) from `results_ready` back to `planned`, nulling their timestamps.

*No response data was lost* — only status and timestamps were touched. All four
were restored, with `opened_at`/`closed_at` reconstructed from the responses'
own timestamps, so those two are approximate. `dismissed_at` was set on the
PSY240 row to stop the morning's results resurfacing on 199 phones at midnight;
clearing it would show them again.

**A blanket `taskkill //IM node.exe`** to stop the run also killed the Supabase
MCP servers, costing database tooling for the rest of the session.

**The lesson worth keeping:** the harness was carefully scoped — a scratch
class, a `loadtest+` email prefix, a dry-runnable teardown — and none of that
helped, because the damage came from an *ad-hoc* query typed outside the
harness, at speed, at midnight. Scope the query, not just the tool.

---

## Why it stopped at 150

The dedupe bug meant the remaining levels would have produced no write data,
and two production mistakes had already happened inside fifteen minutes. The
capacity question was answered; continuing risked more damage for data the
run could no longer collect.

Teardown was clean: class, lecture, check-ins, 300 members and 300 users all
removed, zero orphans, both real classes verified intact.

---

## What is still unknown

- **Behaviour above ~113 concurrent.** Untested. The flatness to that point and
  2.4% CPU make a cliff before 200 unlikely, but it is an inference.
- **The three-hour soak.** `nano` died from *cumulative* credit drain, not
  instantaneous load. At 2–4% CPU that cannot happen — but it was not measured
  over hours.
- **The real sign-in wave.** The harness never exercised roster-join, Resend, or
  `verifyOtp`. Separately diagnosed from L1's own data: PSY240 joins ran every
  ~30 s until **09:07:57**, then stopped dead for **52 minutes**. PSY309 the day
  before — 49 students, same `nano` — showed no such wall. The wave tipped the
  instance over; the instance was the cause.

## Re-running

```bash
node scripts/loadtest/setup.mjs --users 300
node scripts/loadtest/run.mjs --levels 150,200,250,300 --hold 480
node scripts/loadtest/metrics.mjs --every 20   # in parallel
node scripts/loadtest/teardown.mjs
```

Both harness bugs above are fixed, so a re-run would reach the top levels. It
needs `SUPABASE_SERVICE_KEY` (an `sb_secret_` key) in `.env.local`, removed
afterwards. Run it when no students are on the system.
